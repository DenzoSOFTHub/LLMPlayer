# JVM tuning properties — full reference

Every property below is set with `-Dproperty=value` on the Java command line. `CLAUDE.md` carries
only the handful that change correctness or that are known dead ends; this file is the complete
matrix.

Flags marked **measured dead** should not be enabled on current hardware — they are kept only so a
future session does not re-attempt them without reading the measurement first.

## CUDA execution mode

| Property | Default | Description |
|----------|---------|-------------|
| `cuda.nograph` | `false` | Disable CUDA graph capture; use per-layer kernel launches instead. Note that disabling graph mode crashes PPL from 1.00 to 0.07 on some models while changing tok/s by only about 10% — the graph baseline matters for quality, not just speed. |
| `cuda.cublas` | `false` | Enable cuBLAS for Q4_K matmul (pre-dequantizes to FP16; requires `libcublas.so`). |
| `cuda.cublas.fp32` | `false` | Use FP32 instead of FP16 for cuBLAS dequantization (more VRAM, slower). |
| `cuda.debug` | `false` | Print the full stack trace when GPU forward-pass init fails instead of just the message; also makes `BatchedCudaForwardPass` synchronize after each launch to pinpoint async failures. |
| `cuda.batched` | `false` | **Experimental.** Enable the batched GPU forward pass (`BatchedCudaForwardPass` + `matmul_q4_k_dp4a_batched.cu`) for `forwardBatch()` and speculative-decoding verification, processing K tokens in one pass so the weight read amortizes over K. Default off: the batched path currently fails at the quantize launch with CUDA error 400 when sharing a context with the single-token `CudaForwardPass` (handles are valid; a context/launch-interaction bug is under investigation) and poisons the context. The default `forwardBatch` is the correct sequential `forwardSingleToken` loop. The batched matmul kernel is correct standalone. |
| `cuda.prebuilt` | `false` | Load prebuilt cubin artifacts instead of NVRTC runtime compilation. Measured within ±1% of NVRTC because both share the ptxas backend (see `option-a-ptx-attempt.md`); no prebuilt artifacts are shipped. `cuda.prebuilt.verbose` adds loader logging. |

## dp4a integer matmul

| Property | Default | Description |
|----------|---------|-------------|
| `cuda.dp4a` | `true` | Master switch for `__dp4a` integer dot product on `CudaForwardPass`, `Qwen35CudaForwardPass`, and `NemotronHCudaForwardPass`. Covers Q3_K (code 3), Q4_K (4), Q5_K (5), Q5_0 (50), Q8_0 (80), IQ4_NL (41), IQ4_XS (42). Quantizes the input to Q8_1 then uses int8 dp4a. Measured **+34% on Llama-1B** (47→63 tok/s on RTX 4050), **+92% on Nemotron-3-Nano-4B** (10.4→20.0), **+42% on Phi-3-mini IQ4_NL**, **+15.5% on Llama-3.2-3B Q3_K_L** (12.5→14.5, added in v1.13.0). |
| `cuda.dp4a.q3` | `true` | Use the Q3_K dp4a kernel (`matmul_q3_k_dp4a.cu`, v1.13.0). The 110-byte block is not 4-byte aligned so the kernel is constrained to byte `__ldg`, but unlike Q6_K the scale decode is cheap enough that dp4a still wins: 12.5 → 14.5 tok/s (+15.5%) on Llama-3.2-3B Q3_K_L. Opt out if a future model regresses. Wired in all three forward passes. |
| `cuda.dp4a.q5` | `true` | Use the Q5_K dp4a kernel. Opting out falls back to the FP32 Q5_K kernel for both per-layer matmuls and the output projection. |
| `cuda.dp4a.q6` | `false` | Enable the Q6_K dp4a kernel (rewritten 2026-04-14, bit-equivalent to FP32). **Default off because it is slower** than the FP32 Q6_K kernel (70.6 vs 72.85 tok/s on Llama-1B): the 210-byte block is not 4-byte aligned, so the kernel must use byte loads and that overhead overwhelms the dp4a benefit. Kept for correctness checks. |
| `cuda.dp4a.outputs` | `true` | Route the output (final logit) projection through dp4a on `Qwen35CudaForwardPass`. Flipped from opt-in to default-on in v1.14.0 (+9–11% on Qwen3.5 4B/9B). |
| `cuda.dp4a.iq4xs.mw` | `true` | Use the multi-warp IQ4_XS dp4a kernel (`matmul_iq4_xs_dp4a_mw.cu`). |
| `cuda.dp4a.fused_gate_up` | `false` | Use a single fused kernel for the gate+up dp4a matmuls (`matmul_q4_k_dp4a_fused_gate_up.cu`). Measured marginal-to-regression on Llama-1B (70.9 vs 73.5 with separate dp4a) because the input was already L1-cached and the fused kernel adds register pressure. |
| `cuda.dp4a.mw` | `false` | Use the llama.cpp-style multi-warp Q4_K dp4a kernel (`matmul_q4_k_dp4a_mw.cu`: 4 warps × 32 lanes per row, 1 row per block). Slower for small models (Llama-1B: 51 vs 70 tok/s) due to per-block overhead; may help larger models with more super-blocks per row. |
| `cuda.dp4a.mmvq` | `false` | Port of llama.cpp's `mul_mat_vec_q` for Q4_K. Measured neutral-to-slower on RTX 4050 (see `llamacpp-comparison.md`); kept for reference. |
| `cuda.dp4a.bypass` | `false` | Debug flag — force all dp4a-eligible matmuls back to their FP32 kernels without disabling the rest of the dp4a infrastructure (the Q8_1 quantize launches still run). Useful to isolate whether a quality issue comes from int8 quantization. |
| `cuda.fused_norm_quantize` | see note | Fused RMSNorm + Q8_1 quantize kernel, saving one launch and one HBM round-trip per layer. Default **on** in `CudaForwardPass` when dp4a is active; **opt-in** on `Qwen35CudaForwardPass`. Mathematically identical output. |

## Per-kernel variant selection

| Property | Default | Description |
|----------|---------|-------------|
| `cuda.q5k.smem` | `true` | Shared-memory input kernel for Q5_K (+7% throughput). |
| `cuda.q6k.tiled` | `true` | Tiled shared-memory kernel for Q6_K (256-element tiles, +9% throughput). |
| `cuda.q5_0.smem` | `true` | Shared-memory Q8_1 input cache for Q5_0 dp4a (`matmul_q5_0_dp4a_smem.cu`, v1.13.0). Targets Gemma-3 Q4_K_M, whose Q/K/gate/up are Q5_0. Measured **+2–3%** on Gemma-3 1B/4B — graph mode amortizes most of the win, so no-graph mode sees more. PPL bit-identical. |
| `cuda.iq4nl.smem` | `false` | Shared-memory Q8_1 input cache for IQ4_NL dp4a (`matmul_iq4_nl_dp4a_smem.cu`, v1.13.0). Measured **neutral** on Phi-3-mini in graph mode (12.0 vs 12.07 tok/s), so kept opt-in. Still useful for the no-graph fallback or hardware with different cache characteristics. |
| `cuda.q6k.smem` | `false` | Shared-memory input kernel for Q6_K (alternative to the tiled variant). |
| `cuda.q4k.coalesced` | `false` | Coalesced Q4_K kernel variant (all threads process the same group). |
| `cuda.q4k.smem` | `false` | Shared-memory input tiling Q4_K kernel variant. |
| `cuda.q4k.2warp` | `false` | Two-warps-per-row Q4_K kernel, splitting column groups between two warps with a shared-memory partial-sum reduction. |
| `cuda.q4k.mr2` | `false` | Two-rows-per-warp Q4_K kernel variant at the tensor layer (`Q4_KCudaTensor`). |
| `cuda.q4k.mr4` | `false` | Multi-row Q4_K dp4a kernel (`matmul_q4_k_dp4a_mr4.cu`: 4 rows per warp, 4 warps per block = 16 rows per block). Already present on `Qwen35CudaForwardPass`; mirrored into `CudaForwardPass` in v1.13.0. Opt-in because mr4 trades per-block overhead for weight-matrix reuse, a net loss on small models — Llama-1B regresses. |
| `cuda.q4k.cpasync` | `false` | **Measured dead** — cp.async input-prefetch Q4_K kernel, -2.8% on Llama-1B (see `option-c-cpasync-attempt.md`). Do not enable on current hardware. |
| `cuda.deltanet.v2` | `true` | Use the float4-vectorized DeltaNet kernel (+4% throughput). |
| `cuda.mamba.smem` | `false` | Shared-memory Mamba-2 scan kernel (`mamba2_scan_smem.cu`) on `NemotronHCudaForwardPass`, caching per-group B and C in shared memory. Within measurement noise on RTX 4050 — the Mamba phase is matmul-bound on GPU and the scan kernel is a small fraction of per-token time. |
| `cuda.fuse.qkv` | `false` | Runtime QKV weight fusion — concatenate separate Q/K/V weights at init into one GPU buffer and activate the merged-matmul + `split_qkv.cu` path. Saves two kernel launches and two redundant Q8_1 input reads per layer per token. Default off because graph mode already amortizes launch overhead (neutral on Llama-1B Q4_K_M in graph mode, about +2% no-graph), and it doubles the QKV weight footprint in VRAM during the init device-to-device copy. |
| `cuda.falcon.dp4a` | `false` | Enable dp4a matmuls in `FalconH1CudaForwardPass`. Measured neutral-to-slower than FP32 on RTX 4050, because Falcon-H1's per-token cost is dominated by the Mamba-2 scan plus many small matmuls, so the per-matmul `quantize_q8` launch outweighs the int8 speedup. LFM2 and the Granite MoE experts *are* default-on under the global `cuda.dp4a` — they measured +37% and +124% respectively. |

## Memory and cache

| Property | Default | Description |
|----------|---------|-------------|
| `cuda.kv.fp16` | `false` | Store the GPU KV cache as 16-bit half instead of FP32 (`CudaForwardPass`, all dense architectures). Halves both KV read bandwidth in attention and KV VRAM. Uses `attention_f16.cu` (`kv_cache_update_f16` + `attention_full_f16`) with inline PTX `cvt.f32.f16` / `cvt.rn.f16.f32`, so NVRTC needs no toolkit include path. Measured on Llama-3.2-1B Q4_K_M: **+17% at about 400 tokens of context** (74.8 → 87.6 tok/s), growing with context; neutral at short context. PPL preserved at 0.95. Default off to keep bit-exactness for regression testing. Note that the KV-aware placement budget auto-enables this when FP32 KV would not fit all layers but FP16 KV would. |
| `kv.q8` | `false` | Q8_0 block-quantized KV cache (1.125 vs 4 bytes per element; **+28% faster** for DeepSeek2 MLA). |
| `kv.q4` | `false` | Q4_1 block-quantized KV cache (0.75 vs 4 bytes per element, **5.33× smaller**), reconstructed as `val = q*d + m` with `q ∈ [0,15]`. Wins over Q8 on bandwidth-bound attention. Measured on DS-Coder-V2-Lite Q4_K_M CPU at ctx=512: F32 2.5 tok/s → Q8 2.2 → **Q4 3.2 (+28% vs F32, +45% vs Q8)**, PPL 1.23 → 1.32 → 1.54 (all rated excellent). Takes precedence over `kv.q8` when both are set. |
| `moe.expert.cache.experimental` | `false` | Enable the Q4_K/Q5_K/Q6_K expert GPU cache path in `ExpertGpuCache`. The MXFP4 (GPT-OSS) path is validated and always on; the K-quant path currently **produces incorrect output** (a byte offset / kernel mismatch under investigation) — keep off for production. `moe.cache.debug=true` adds cache logging. |
| `gemma.ple.gpu` | `false` | Keep the Gemma 4 / 3n PLE tensors GPU-resident instead of the default CPU placement. Debug and benchmarking only — PLE is a per-token lookup, so GPU residency wastes VRAM. |
| `preload` / `no.preload` | auto | Force or skip the full-file mmap preload. By default `LLMEngine.load` skips preload when the model exceeds 85% of physical RAM (lazy mmap — only the working set pages in, and cold MoE experts stay on disk) and sets the internal `mmap.advise` property by access pattern: `random` (MADV_RANDOM) for MoE, where expert touches are sparse and read-ahead should be off, or `sequential` (MADV_SEQUENTIAL) for dense models, whose per-token layer walk is cyclic-sequential so read-ahead should be up and used pages dropped first. |
| `prefill.batched` | `true` | Layer-outer prefill. **Standard engine** (Llama, Qwen2/3, Mistral, SmolLM3, Granite, Gemma 2/3, …; `InferenceEngine.forwardPrefill`) and **Qwen3.5** (`Qwen35InferenceEngine.forwardPrefill`: DeltaNet and attention projections batched, recurrence per token; 0.8B 1.75×, 4B 1.43×): the prompt goes through each layer in chunks and every projection runs as one multi-token matmul (`FloatTensor.matmulRowsBatch`, with four-token kernels for Q4_K, Q6_K and Q8_0), while attention stays token by token in position order. Measured back to back on ~290-token prompts: Llama-3.2-1B 117.7 s → 31.4 s (3.7×), Qwen2.5-Coder-3B 745.8 s → 217.9 s (3.4×), generated text identical. Layers it does not cover (merged QKV, packed gate/up, parallel FFN, post-norm only, flash attention, GPU pass) fall back to the per-token loop automatically. See [`cpu-dispatch-and-kernels.md`](cpu-dispatch-and-kernels.md). **Qwen3 MoE and DeepSeek2** (`forwardPrefill`): drives the layers in the outer loop and the prompt tokens in the inner loop with identical per-(layer, token) arithmetic, so output is bit-identical; it collapses the working set from `layers × top-K` experts to the union selected by one chunk at one layer. **Measured on Qwen3-Coder-30B with a 109-token prompt: 283.2 s → 65.7 s (4.3×), misses 19989 → 14774, time in disk reads 52.8 s → 17.9 s, PPL unchanged.** Set `false` to restore the per-token loop everywhere. |
| `prefill.batch` | `64` | Tokens per layer-outer prefill chunk. For MoE, larger amortises each expert read over more tokens but grows the per-layer expert union, which must still fit the cache. For the standard engine it sizes the per-token buffers (`PrefillBatch`: about `chunk × (3·dim + 2·qDim + 2·kvDim + 2·ffnDim)` floats, 4 MB on Llama-1B). |
| `moe.top.k` | model's own | Route to fewer MoE experts than the model specifies, as an explicit speed-for-quality trade (`--expert-top-k N`). Expert work scales linearly with the count, and the routed experts are 1.81 G of the 3.04 G parameters touched per token on Qwen3-Coder-30B, so halving the count removes about a quarter of the total and proportionally fewer experts are read from disk. Applied at selection time, so renormalising paths keep the gate mass at one; values at or above the model's own top-K are ignored. **Measured on Qwen3-Coder-30B (native top-8): top-6 and top-4 produce output identical to top-8, top-2 collapses into gibberish.** Note that the perplexity evaluator reported EXCELLENT for that gibberish — judge this knob by generated text at `--temperature 0`, not by PPL. See [`per-token-latency-analysis.md`](per-token-latency-analysis.md). |
| `moe.expert.cache` | `auto` | SSD-streaming RAM cache for MoE routed experts (`MappedExpertCache`, lever L1). Caches whole expert slices — gate, up and down together as one eviction unit — filled by `FileChannel.read(ByteBuffer, position)` straight into off-heap slots, with least-frequently-used retention so the hot experts stay resident. `auto` enables it exactly when the lazy >RAM MoE path is active (`mmap.advise=random`); `true` / `false` force it. Falls back to the mmap path on any failure, and is skipped when the GPU expert cache owns the path. **Measured on Qwen3-Coder-30B (18.6 GB against 7.8 GB RAM, 2 GB cache): 34.1 s vs 107.9 s for five tokens — 3.2×**, output and PPL bit-identical, 48.4 % hit rate, 7.42 GB read in 4.2 s. Full analysis in [`ssd-streaming-cache.md`](ssd-streaming-cache.md). |
| `moe.expert.cache.mb` | auto | RAM budget in MB for the above, also settable as `--expert-cache-size`. Default is a quarter of physical RAM capped at 4 GB. Slots are sized by the largest expert across all MoE layers, so a Q4_K_M mix with Q6_K `ffn_down_exps` on some layers sizes every slot to that; the startup line reports the resulting slot count. Below 8 slots the cache declines to start. **More is not monotonically better**: on the reference box a 3 GB budget reached the best hit rate of the sweep (57.3 % vs 48.4 % at 2 GB) and still ran 4× slower end to end, because cache plus heap starved the page cache that absorbs every miss. A warning is printed when budget + heap exceeds 60 % of physical RAM. |
| `moe.expert.willneed` | `auto` | Expert-granular read-ahead for MoE models streamed from SSD (`ExpertPrefetch`). Right after the router picks top-K, issues one `madvise(MADV_WILLNEED)` per selected expert slice, before the expert matmuls touch them. This overrides the blanket `MADV_RANDOM` for those ranges, which is what you want: expert access is random *between* experts but strictly sequential *within* one contiguous ~2.6 MB slice. `auto` enables it exactly when the lazy >RAM MoE path is active (`mmap.advise=random`); `true` / `false` force it. A hint only — it never changes results. **Measured ~1.15× on Qwen3-Coder-30B** (93.9 s vs 107.9 s for five tokens, 18.6 GB model against 7.8 GB RAM), which is below this box's noise threshold: a `mincore()` probe shows `MADV_WILLNEED` over a 2.65 MB range returns success but leaves only 32 of 647 pages resident, because `vboxsf` caps read-ahead near 128 KB. Kept on because it is never negative and should do better on storage that honours the hint. Full analysis in [`ssd-streaming-cache.md`](ssd-streaming-cache.md). |
| `mmap.prefetch` | `auto` | Next-layer mmap prefetch for dense lazy (larger-than-RAM) loads via `LayerPrefetcher`: while the CPU loop computes layer N, a background thread pages in layer N+1's weight range from the GGUF `blk.N.*` tensor offsets, overlapping disk I/O with compute — the AirLLM prefetch pattern. `auto` means on when `mmap.advise=sequential`; `false` disables; `true` forces. It uses a single-slot discard queue so a lagging disk drops requests harmlessly, starts at the first CPU-resident layer, and wraps past the last layer. MoE lazy loads get no prefetcher because routed-expert access is unpredictable. |

## CPU matmul and attention

| Property | Default | Description |
|----------|---------|-------------|
| `matmul.tiled` | `false` | **Measured dead** — benched 2026-04-15 on Llama-3.2-1B Q4_K_M CPU at -50% (3.0 vs a 5.6–8.0 tok/s baseline). The per-block `MemorySegment.copy` plus `ROW_TILE=4` overhead outweighs L1 input reuse, because `SimdQ4_KFloatTensor.dot` already reads directly from the segment. Kept opt-in for future hardware where L1 reuse might dominate; do not enable on current targets. |
| `matmul.pool` | `true` | Route CPU matmuls, per-head attention and per-expert MoE loops through `MatmulPool`: persistent platform workers with dynamic chunk claiming, so faster or less loaded cores take more work. Replaces `VirtualThreadMatmul` and the ForkJoin streams. **1.28–1.77× decode on Llama-3.2-1B** (in-process A/B against the old dispatcher, same kernels). Disabled automatically when a GPU backend initialises; `false` restores the old dispatchers, `force` keeps the pool on under a GPU backend. See [`cpu-dispatch-and-kernels.md`](cpu-dispatch-and-kernels.md). |
| `matmul.threads` | from `--threads` | Pool size. The launcher sets it from `--threads` (default: physical cores) in every launch mode, including `--web` and the GUI, where `--threads` previously had no effect. |
| `matmul.chunks.per.thread` | `4` | Target chunks per thread per dispatch. More balances uneven cores better; fewer costs less claiming overhead. |
| `matmul.min.chunk` | `32` | Minimum rows per chunk for single-token matmuls; kernels prepare the input once per chunk (Q4_K permutes it and computes sub-block sums). |
| `matmul.warmup.ms` | `1500` | Before the first batched prefill, run each weight class's single-token kernel on 64 rows until it is JIT-compiled (an iteration under half the first) or this many ms pass. Without it, batched prefill left the decode kernels uncompiled until decode began, and decode ran on C1 code for most of a short generation (Llama-1B: 3.8–7.4 against 8–11.8 tok/s). `0` disables. |
| `matmul.spin` | `20000` | Spin iterations a worker waits for the next dispatch before parking. |
| `q6k.repack` | `false` | **Opt-in.** On first use by the dense matmul paths, rewrite each Q6_K tensor into an off-heap int8 layout (276 bytes per 256 weights: `q − 32`, the 16 scales, `d` as float). Lossless: every `q − 32` fits an int8 and `d·sc` is exact in float32, and generated text is byte-identical. The kernel gets the Q8_0 shape and runs **2.2× faster single-thread** (Llama-1B `output`/`ffn_down`), and batched prefill gains 1.21×, but **decode was slower** in 9 of 10 paired runs on the reference VM, because multi-threaded decode is memory-bandwidth bound and the copy is 1.31× the bytes. Re-measure on hosts with more bandwidth per core. Never applied to lazy larger-than-RAM loads; `dot()` (MoE expert slices) keeps the original layout. See [`cpu-dispatch-and-kernels.md`](cpu-dispatch-and-kernels.md). |
| `attn.flash` | `false` | FlashAttention online-softmax, single-pass. About 10% slower on Java/CPU, so opt-in. |
| `gemma4.nople` | `false` | Disable PLE pre-computation in the Gemma 4 forward pass (debug flag). |

| `cuda.profile.mamba` | `false` | Fine-grained Mamba-2 sub-kernel timing on `NemotronHCudaForwardPass`. Requires `cuda.profile=true`. |
| `qwen35.profile` | `false` | Per-kernel timing on `Qwen35CudaForwardPass` plus per-phase hooks in `Qwen35InferenceEngine` — the Qwen3.5 counterpart of `cuda.profile`. |

## Automated kernel autosearch

`./autosearch.sh <model.gguf> [runs_per_config] [min_ppl]` runs a Karpathy-style greedy coordinate
ascent over the entire flag matrix above. For each flag it toggles the value, runs N benchmarks
(best tok/s wins), and accepts the change only if tok/s improves **and** PPL stays at or above
`min_ppl`; otherwise it reverts. The output is the optimal configuration plus the speedup over
baseline, written to `autosearch-results.txt`.

Empirically on RTX 4050 with Qwen3-4B Q4_K_M, the defaults are already Pareto-optimal — no flag
toggle improves tok/s without degrading PPL. The CUDA-graph baseline is the critical one: disabling
it crashes PPL from 1.00 to 0.07 even though tok/s changes by only about 10%.
